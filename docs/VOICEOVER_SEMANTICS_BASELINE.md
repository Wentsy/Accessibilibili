# Accessibilibili VoiceOver 語義基準

這份文件記錄 Accessibilibili 最核心的無障礙設計原則之一：**一個可操作的內容項目，應該盡量對應一個完整、穩定的 VoiceOver 語義節點。**

這套行為不是 PiliPlus 官方版本原本就具備的。早期無障礙改造中，部分影片與評論頁面的語義結構非常碎片化；Accessibilibili 後續持續整理成「一滑一整條」的閱讀方式。這項改造有一部分早於目前的維護紀錄，曾由 Hermes 協助處理，之後又在目前 fork 中繼續統一與修正。

本文件的用途，是避免未來同步 PiliPlus 上游版本時，因 widget 重構或 semantics 結構變動，把這個已經成熟、實際可用的行為弄丟。

## 第一原則：一滑就是一個完整內容單位

VoiceOver 左右滑動時，使用者應該以「內容」為單位閱讀，而不是以畫面上每一小塊 Text、Icon、Badge 為單位閱讀。

### 影片卡

理想行為：

一次左右滑動聚焦到一支影片時，就能連續聽到這支影片的主要資訊，例如：

```text
影片標題，UP 主，時長／觀看進度，播放量，彈幕量，發布時間
```

時間等次要資訊應放在最後，不應搶在標題之前。

不應退化成：

```text
第一滑：12 分 34 秒
第二滑：影片標題
第三滑：UP 主
第四滑：播放量
第五滑：9 月 2 日
```

也不應讓封面、角標、時長 Badge、播放量 Icon 等裝飾性子元件各自變成 VoiceOver 焦點。

目前常見的實作方式是：

- 外層 `Semantics` 代表整張影片卡。
- `container: true`。
- `explicitChildNodes: false`。
- 視情況使用 `excludeSemantics: true` 或 `ExcludeSemantics`，避免內部 Text／Icon／Badge 再被逐一讀取。
- 由外層 `label` 組合真正需要朗讀的資訊。
- 點兩下仍然開啟影片。
- 點讚、分享、稍後再看、造訪 UP 主、更多等功能，優先使用 `CustomSemanticsAction`，不要為了這些操作把整張卡拆成大量焦點。

## 評論同樣遵守「一則評論＝一個語義節點」

評論區比影片卡更需要避免碎片化。

理想行為：

VoiceOver 聚焦一則評論時，應該一次讀完整則評論的核心資訊，例如：

```text
評論者，身份／必要狀態，評論內容，讚數，回覆數，評論時間
```

評論時間放在最後，例如：

```text
3 小時前評論
9 月 2 日評論
```

不應退化成以下混亂情況：

- 有些評論一次讀完整條，有些卻被拆開。
- 第一滑只讀評論者，下一滑才讀評論內容。
- 讚數、回覆數、圖片提示、時間各自變成獨立焦點。
- 樓中樓和主評論使用不同的語義規則，導致操作方式不一致。

主評論與樓中樓都應盡量共用一致的語義策略。

目前共用評論語義的重要入口之一：

```text
lib/common/a11y/reply_semantics.dart
```

其中外層語義節點應負責：

- 完整評論 label。
- 評論時間。
- 點讚／取消讚。
- 點踩／取消踩。
- 點兩下展開／進入需要的評論內容。
- VoiceOver 聚焦後與真實 viewport 的同步。

評論內部的視覺子元件不應重新搶走焦點。

## 應套用這個原則的頁面

只要是「一列／一卡代表一個內容實體」的地方，都應優先檢查是否符合這套語義基準。

至少包括：

- 首頁 Web 推薦。
- 首頁 App 推薦。
- 搜尋結果影片。
- UP 個人頁影片。
- 相關影片／推薦影片。
- 觀看紀錄。
- 稍後再看。
- 其他使用共用水平／垂直影片卡的頁面。
- 主評論區。
- 樓中樓評論。

未來如果新增其他影片列表，也應優先沿用共用影片卡的完整語義，而不是重新讓子元件自行暴露給 VoiceOver。

## 與 viewport／翻頁機制的關係

「一滑一整條」不是獨立的小功能，它和目前的焦點／viewport 同步、三指翻頁、lazy list semantics 建立是同一套使用體驗。

必須同時維持：

1. 左右滑一次移動到下一個完整內容節點。
2. 焦點移動時，實際畫面要跟著移動。
3. 接近 lazy list 語義邊界時，要能提前建立後續項目，避免 VoiceOver 發出邊界音效後無法繼續。
4. 三指翻頁後，新的畫面內容仍然保持同樣的完整語義節點。
5. 分頁載入後，不可以因 rebuild 把焦點跳回第一項。

因此，上游如果修改以下類型的程式，需要同時重新驗證本文件：

```text
Semantics
ExcludeSemantics
ListView
GridView
SliverList
SliverGrid
ScrollView
影片卡 widget
評論 widget
列表 item widget
```

## 上游同步時的高風險訊號

如果合併 PiliPlus 官方更新後出現以下任何一項，就代表這套語義基準可能退化：

- 一支影片需要滑兩次以上才能把標題與基本資訊聽完整。
- VoiceOver 先讀時長，再讀標題。
- 封面、時長 Badge、播放圖示各自成為焦點。
- 有的評論一次讀完整，有的評論者與內容被拆成兩個焦點。
- 樓中樓的語義順序與主評論不同。
- 左右滑需要穿過大量沒有操作價值的裝飾元素。
- 同一張影片卡或同一則評論被重複朗讀。
- 卡片的自訂操作消失，只剩長按或視覺按鈕可用。

出現以上情況時，不應把它視為「官方原本就是這樣」而接受；對 Accessibilibili 而言，這是無障礙 regression。

## 快速驗收方式

同步上游後，打開 VoiceOver，至少做以下測試：

### 首頁影片

- [ ] 從第一支影片開始向右滑。
- [ ] 每次只需要一次滑動就能移到下一支影片。
- [ ] 每支影片一次朗讀標題與主要資訊。
- [ ] 時長／播放量／發布時間等資訊不會各自變成獨立焦點。
- [ ] 發布時間位於整條資訊後段。
- [ ] 實際畫面跟著 VoiceOver 焦點移動。

### 其他影片列表

至少抽查：

- [ ] 搜尋結果。
- [ ] UP 個人頁。
- [ ] 觀看紀錄。
- [ ] 稍後再看。
- [ ] 相關影片。

規則和首頁相同：一支影片應是一個主要語義節點。

### 評論區

- [ ] 主評論一次滑動聚焦一整則評論。
- [ ] 評論者與評論內容不被拆成兩次滑動。
- [ ] 讚數、回覆數、評論時間不會各自形成無意義的獨立焦點。
- [ ] 評論時間在最後。
- [ ] 樓中樓與主評論使用一致的閱讀方式。
- [ ] 左右連續瀏覽時不觸礁、不跳回第一則。

## 維護判斷原則

如果上游重寫了影片卡或評論結構，不要單純把舊 widget 整份蓋回去。

正確方式是：

1. 保留上游的新功能與 bug fix。
2. 找出新 widget 中代表「一支影片」或「一則評論」的最外層邏輯單位。
3. 在該層重新建立完整 `Semantics`。
4. 排除沒有獨立操作價值的內部語義。
5. 把必要的額外操作改成 `CustomSemanticsAction`。
6. 再跑本文件的實機驗收。

最重要的不是保留某一段舊程式碼，而是保留這個使用者體驗：

> **VoiceOver 左右滑時，使用者是在瀏覽「影片」和「評論」，而不是在瀏覽 Flutter 畫面上被拆碎的 Text、Icon 和 Badge。**
